# T536 双板互操作实测结果（2026-10-23）

本报告记录 canopen-rs 当前工作区在 **两块真实 T536 开发板** 上的 CANopen
互操作验证，以及与 **CANopenLinux（C）**、**python-canopen（Python ref）**
的互相通信。

> 实板结果与 vcan 模拟结果分开记录；本报告全部为 SocketCAN 物理总线结果。
> harness 与日志位于仓外 `/tmp/canopen-interop`，未修改 `ref/`。

## 1. 硬件与拓扑

| 板卡 | 型号 | 测试接口 | 对端 |
|---|---|---|---|
| `192.168.31.120` | T536-Leice | `can0` | `.63 can1` |
| `192.168.31.63` | TLT536-EVM HDMI | `can1` | `.120 can0` |

- 物理 CAN 直连，两端 500 kbit/s，sample-point 0.875，`restart-ms 100`。
- 节点 ID：Rust/Python/C 从站均为 **5**；C 主站网关自身节点 **127**。
- 测试结束链路计数（两板合计）：
  - `.120 can0`：RX 2709 / TX 2868，errors=0，dropped=0
  - `.63 can1`：RX 2868 / TX 2709，errors=0，dropped=0
- 两板均可 `root` 直登；板端无 Rust 工具链，Rust 二进制由主机交叉编译后部署。

## 5. 限制与说明

1. Python `LocalNode` 没有自动 TPDO 发送逻辑，因此 Python 作为 server 时
   PDO 不参与；Python 作为 client 对 Rust server 的 PDO 已通过。
2. C CiA-309 网关不提供 PDO/心跳 client API，因此 C 作为 client 的用例
   不覆盖 PDO/心跳；C 作为 server 时由 Rust client 覆盖 PDO。
3. C 参考 demo OD 默认没有 0x1008/0x2000 等对象；测试用 `/tmp` 副本扩展了
   OD，未修改仓库 `ref/`。
4. C demo 需要预置持久化哨兵文件避免 0x5000 EMCY 停在 pre-operational；
   这是 demo 环境行为，不是协议栈差异。
5. 未做电气故障注入（总线短路、终端缺失、bus-off 恢复压力）；未观测物理
   LED（LED 逻辑由 `Node::leds()` 与单元测试覆盖）。
6. `.63 can0` / `.120 can1` 未接对端，保持 down；测试只使用 `.63 can1` ↔
   `.120 can0`。

## 6. 结论

当前工作区的 Rust CANopen 栈与 C（CANopenLinux）和 Python（python-canopen）
参考栈在真实 T536 双板上完成四向互操作，全部通过；本轮新增的 LSS identify、
guarding 生命期、TIME 0x1012/0x1013 写守卫与 NMT startup-to-Operational
也在实板上通过。未发现需要回写 `docs/DESIGN-DECISIONS.md` 的新缺陷。
